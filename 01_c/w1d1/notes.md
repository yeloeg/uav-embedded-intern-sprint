| `swap_int` | 用临时变量三步交换 | ✅ |
| `swap_generic` | 按字节交换，每轮 `tmp[i] = pa[i]; pa[i] = pb[i]; pb[i] = tmp[i];` | ✅ 通过测试，但见下面「待改进」 |

**待改进的一处**：`swap_generic` 里的 `tmp[64]` 是按固定 64 字节定义的，但函数没有检查 `size`。
如果哪天有人用它交换一个 128 字节的结构体，`tmp[i]` 就会写越界，破坏栈上的其他数据——
而且这种错误往往在函数返回后才爆炸，非常难查。
加固方法很简单，函数开头加一句：

```c
if (size > sizeof(tmp)) {
    return;   /* 或者改成用 memcpy 分块交换，或断言报错 */
}
```

> 这条正好呼应今天的 Q1：**边界条件不检查，就是把未定义行为埋进代码里**。

## 三、自测问题 1：memcpy 遇到内存重叠会怎样？

### 🎤 30 秒口述版
> `memcpy` 的标准里明确规定：源和目标内存**不能重叠**，一旦重叠就是未定义行为。
>
> 原因是 `memcpy` 是性能优先的接口——实现可以按机器字长甚至 SIMD 批量搬运，编译器也能把它内联展开，
> 这些都建立在「两块区间互不干扰」的前提上。真重叠了会怎样？典型的 `memcpy` 是从低地址往高地址逐字节复制，
> 如果目标地址比源地址高、区间又交叠，前面几个字节就会把还没读到的源数据覆盖掉，结果复制出一串被污染的数据，
> 比如想把 `ABCDEF` 往后挪两格，最后得到的是 `ABABAB`。
>
> 标准之所以不说"重叠时该怎么办"，是因为规定一种错误用法的行为会限制实现自由：与其定义它，
> 不如直接标成未定义，把责任交给调用者。要处理重叠就用 **`memmove`**，它内部会先判断方向——
> 目标在源后面就从高地址往低复制，否则从低往高，代价是多一次分支判断，所以通常比 `memcpy` 略慢。

### 机制拆解

**① 标准怎么说的**

C 标准（C11 §7.24.2.1）原话是：如果复制发生在相互重叠的对象之间，行为未定义。
标准只保证"不重叠时按字节正确复制"这一种用法。

**② 重叠时到底坏在哪**

假设把 `ABCDEF` 从地址 0 挪到地址 2（区间重叠），实现从低地址往高地址逐字节复制：

| 步骤 | 操作 | 内存变成 |
|---|---|---|
| 初始 | — | `A B C D E F` |
| i=0 | `dst[0] = src[0]`，即 cell2 ← 'A' | `A B A D E F` |
| i=1 | cell3 ← 'B' | `A B A B E F` |
| i=2 | cell4 ← src[2]，但 cell2 已经变成 'A' 了 | `A B A B A F` |
| i=3 | cell5 ← src[3]，即 'B' | `A B A B A B` |

期望结果是 `ABCDEF`，实际得到 `ABABAB`——**源数据在读取之前就被自己写坏了**。

**③ 为什么标准选择"未定义"而不是规定一种行为**

- 规定重叠时的正确结果，就等于要求所有实现都做方向判断，`memcpy` 的性能优势直接没了；
- 编译器需要 `memcpy` 的 `restrict` 语义来向量化（一次搬 16 字节、32 字节），这要求区间互斥；
- C 标准的一贯做法是：对不该出现的用法直接标 UB，把保证正确性的责任交给程序员，换取实现的自由和性能。

**④ memmove 为什么能处理**

它先比较两个地址：目标在源之后且重叠 → 从**高地址往低**复制；否则从低往高。多一次判断，换来正确性。
`memcpy` 比 `memmove` 快的那一点，本质就是省掉了这个判断（以及由此得到的向量化机会）。

### 可能被追问

| 追问 | 怎么答 |
|---|---|
| 你写的 `my_memcpy` 重叠了会怎样？ | 我的实现就是从低到高逐字节复制，所以当 `dst` 落在 `(src, src+n)` 里时会污染源数据，结果不可预测——和标准描述的一致 |
| 为什么 `memcpy` 比 `memmove` 快？ | 一是语义上可以用 `restrict`，编译器能假定两块不重叠从而向量化；二是 `memmove` 多一次方向判断 |
| 飞控里什么时候必须用 `memmove`？ | 在同一块缓冲区内部搬数据时，比如把环形缓冲区里后续的帧前移、或者 DMA 缓冲重新对齐 |
| `memcpy` 能不能用来拷贝结构体？ | 可以，但要小心对齐和 padding；结构体里有指针或需要深拷贝时不能直接用 |

### 🧠 记忆钩子

> **`memcpy` 用在"两块互不相关的地"，`memmove` 用在"同一块地里挪东西"。**

## 四、自测问题 2：strcpy 的返回值为什么是 char* 而不是 void？

### 🎤 30 秒口述版

> 这是 C 库的一个老约定：字符串函数统一返回**目标指针**，也就是 `dst`，而不是 `void`。
>
> 好处是能链式使用——返回值可以直接塞进别的表达式里，比如 `printf("%s", strcpy(buf, "hi"))`，
> 或者嵌套调用。而且这么做几乎不增加成本，因为实现的时候 `dst` 本来就在手上，
> 返回它只是多用一个寄存器。如果返回 `void`，这些写法就都没了；标准规定返回的是 `dst` 而不是 `src`，
> 因为"操作发生在哪里"才是调用者关心的信息。`strcat`、`memcpy` 也都是这个风格，保持一致。
>
> 不过说实话，这个返回值今天基本是历史遗产了，很少被用到。`strcpy` 真正的问题是
> **它不知道自己能写多少**：没有长度参数，目标缓冲区不够长就直接越界写，而且越界之后是未定义行为。
> 所以工程里我一般不用它，改用 `snprintf(buf, sizeof buf, "%s", src)`，
> 它对长度有约束而且保证结尾有 `'\0'`；或者用 `memcpy` 加显式长度再手动补 `'\0'`。

### 机制拆解

**① 历史约定**

早期 C 库的函数普遍遵循"返回一个有用的指针"的风格：`strcpy` / `strcat` 返回目标指针，
`memcpy` / `memmove` 也返回目标指针。标准化时（C89）保留了这个约定，此后一直没变。
标准原文：`strcpy` 返回 `dst` 的值。

**② 实际用途（链式调用）**

```c
/* 嵌套：把 src 拷到 tmp，再把 tmp 拷到 dst */
strcpy(dst, strcpy(tmp, src));

/* 直接当表达式用 */
printf("复制结果: %s\n", strcpy(buf, "hello"));

/* 拿到目标指针继续处理 */
char *p = strcpy(buf, "hello");
/* p 指向 buf，可以接着做别的 */
```

**③ 为什么不返回 void、也不返回 src**

- 返回 `void` → 链式写法全部失效，却省不下任何东西；
- 返回 `src` → 语义上说不通：调用者关心的是"写到哪里去了"，而 `dst` 就是那个位置；
- 返回 `dst` → 成本几乎为零（指针本来就存在），还保留了组合能力。

**④ 现代观点（面试加分点）**

这个返回值今天很少被用到，一些编码规范反而建议**忽略它**。`strcpy` 的真正缺陷是没有长度参数：
它无法知道目标缓冲区有多大，是缓冲区溢出的经典来源。C11 附录 K 提供了 `strcpy_s`（带长度检查的安全版本），
工程代码更常用 `snprintf` 或"长度 + 内存拷贝"的组合。

### 可能被追问

| 追问 | 怎么答 |
|---|---|
| 返回值一定等于 `dst` 吗？ | 是，标准规定返回 `dst`。我自己的实现也是 `return dst;` |
| 那 `strcat` 呢？ | 同样返回目标指针，风格保持一致，方便链式调用 |
| 你说它危险，具体危险在哪？ | 没有长度参数。目标缓冲区短于 `strlen(src) + 1` 时就越界写，越界后是未定义行为，可能踩坏相邻变量或栈 |
| 那你会用什么替代？ | `snprintf(buf, sizeof buf, "%s", src)`：有长度约束、保证以 `'\0'` 结尾；或者 `memcpy` + 手动补 `'\0'`；C11 有 `strcpy_s` |
| 为什么 `strncpy` 也不推荐？ | 它在源字符串更长时不会补 `'\0'`，容易留下没有结尾的字符串——这是另一个经典坑 |

### 🧠 记忆钩子

> **返回值是"顺手给的遗产"，真正要记住的是：`strcpy` 不知道目标有多大。**
