## 二、内存布局实测（本机真实地址）

```
函数地址       00007ff6 ebdf 1490
字符串常量     00007ff6 ebdf b000   "flight controller"
已初始化全局   00007ff6 ebdf a000   value=42
静态全局       00007ff6 ebdf a004   value=7
未初始化全局   00007ff6 ebdf f030   value=0
静态局部       00007ff6 ebdf f03c   value=1
堆 (malloc)    0000023f f7a6 7c30
栈 (局部变量)  000000b1 2adf fbec
```

**我从地址里看出来的三件事：**

1. **`&g_static_int - &g_global_int = 4`**，正好一个 `int` 的大小 → 已初始化的全局变量和静态全局变量**紧挨着**，它们同在 `.data` 段。
2. 未初始化的全局变量和静态局部变量（`s_counter` 初值为 0）挨在另一块（`.bss` 段），和 `.data` 明显分开。
3. **堆（`0x23f...`）和栈（`0xb1...`）相距极远**，说明它们是两块独立的区域，从两端向中间生长。

**一个重要的提醒**：这是 Windows 上的排布，和嵌入式（ARM GCC + 链接脚本）不一样，**不要死记顺序**。
真正要记住的是"哪些变量属于哪一段"——`代码 → 只读数据 → .data → .bss → 堆 → 栈` 这个分类在任何平台都成立，
但具体地址高低由链接脚本决定。第 2 周看 `.map` 文件时你会看到真实 MCU 上的排布。

## 三、收工前回答 1：环形缓冲区怎么区分空和满？

### 问题的本质

如果让 `head` 和 `tail` 一直往前走，"空"和"满"都会表现为 **`head == tail`**——两种情况撞在一起，无法区分。
所有方案都是为了打破这个歧义。

### 三种常见方案

| 方案 | 空判定 | 满判定 | 最大容量 | 优点 | 缺点 |
|---|---|---|---|---|---|
| **浪费一个槽位** | `head == tail` | `(head + 1) % N == tail` | **N - 1** | 只用两个变量；单写单读时天然安全 | 少存一个；N 很小时浪费比例明显（N=8 少 12.5%） |
| **加计数器** | `count == 0` | `count == N` | N | 空间用满、语义直观 | 多一个共享变量，读写都要维护它，中断场景要额外保护 |
| **序号法**（不取模，只递增） | `head == tail` | `head - tail == N` | N | 用满，且天然区分空满 | 要处理序号回绕（依赖无符号溢出特性） |

### 我用的是哪种、为什么

我用的是**浪费一个槽位**：`full` 判断写成 `(head + 1) % RB_SIZE == tail`。

选它的三个理由：

1. **只需要两个变量**，不用引入 `count`，结构最简单；
2. **单生产者单消费者时不需要加锁**——`head` 只被写者改、`tail` 只被读者改，各自读对方的变量，只要读到的是完整值就安全（这正是后面第 2 周串口收数据的场景：中断负责写，主循环负责读）；
3. **浪费一个字节可以接受**——串口一帧也就几十字节，缓冲区开大一点就行，用复杂度换 1 个字节不划算。

### 🎤 30 秒口述版

> 环形缓冲区的难点在于：如果把 head 和 tail 都做成一直递增的下标，那"空"和"满"都会是 `head == tail`，两种情况撞在一起分不开。
> 打破这个歧义有三种常见做法：浪费一个槽位、加一个计数器、或者用不取模的递增序号。
>
> 我用的是**浪费一个槽位**：空就是 `head == tail`，满就是 `(head + 1) % N == tail`，
> 代价是 N 个字节的缓冲区最多只能存 N-1 个。
> 选它是因为只需要维护两个变量，而且在"中断写、主循环读"这种单生产者单消费者场景下不用加锁——
> head 只有写者会改、tail 只有读者会改，天然没有竞争。少存一个字节，串口那点数据量无所谓。
> 如果缓冲区很小或者空间敏感，我会换成计数器方案，那样能存满，代价是读写都要维护 count，
> 中断里用还得额外做原子性保护。

### 可能被追问

| 追问 | 怎么答 |
|---|---|
| 为什么 `(head+1) % N == tail` 就表示满？ | head 是"下一个要写的位置"，如果它的下一格就是 tail，说明 tail 前面那一格是最后一个空位，再写就要覆盖未读数据了，所以判满 |
| 为什么 count 是 `(head + N - tail) % N`？ | head 走在 tail 前面表示已存数据量；加 N 再取模是为了处理"head 绕回到 tail 前面"的回绕情况 |
| 为什么用 `% N` 而不是 `& (N-1)`？ | 当 N 是 2 的幂时两者等价，但位与更快（一个周期 vs 除法）；只是可读性差一点，所以先写清楚、优化时再换 |
| 缓冲区满了应该怎么办？ | 三种策略：丢弃新数据（返回 -1，我用的这个）、覆盖最老数据、或者让生产者等待/上报丢包。串口场景通常选丢弃并计数 |
| 环形缓冲区和队列有什么区别？ | 环形缓冲区是**用定长数组实现 FIFO 的一种手法**，本质还是队列，只是内存复用、不涉及动态分配 |

### 🧠 记忆钩子

> **少存一个，换来做两个变量、不加锁。**

## 四、收工前回答 2：为什么 `head` / `tail` 要加 `volatile`？

### volatile 到底保证什么

它告诉编译器一句话：**"这个变量可能在你看不见的地方被改掉，每次用它都必须真的去内存读/写。"**

具体保证三件事：

1. 不许把变量缓存到寄存器里反复用；
2. 不许把多次访问合并成一次，也不许整个删掉；
3. 多个 volatile 访问之间的先后顺序要保留（相对彼此而言）。

**不保证**的（这点很多人搞混）：

- 不保证原子性——`size_t` 在 32 位 MCU 上一般是一次访问完成，但 64 位变量、结构体就不是了；
- 不保证多核之间的可见性和内存屏障（那是 C11 `atomic` 的活儿）。

### 具体到环形缓冲区

典型用法是：**中断里 `rb_put()` 写数据，主循环 `rb_get()` 读数据**。
判断有没有数据，靠的就是读 `head`：

```c
while (rb_is_empty(&rb)) {
    /* 等待中断写入数据 */
}
```

如果 `head` 不是 `volatile`，编译器会这样分析：这个循环体里没有任何代码修改 `head`，
所以 `head` 的值在整个循环里都不变 → 于是它**把 `head` 读一次缓存到寄存器里**，
把它优化成"要么直接死循环、要么直接跳过"。
结果就是：中断明明写了数据，主循环却永远看不见，程序卡死。

这类 bug 的可怕之处在于——**编译器换个优化级别、或者你改几行无关代码，现象就会变**，
在调试版上跑得好好的，出 Release 版就死机。

### 飞控里的同类场景

- IMU 中断更新姿态数据 → 主循环读取并打包上传
- 遥控器 SBUS 中断写入通道值 → 主循环解析
- DMA 半满/传输完成中断更新缓冲标志 → 主循环搬运
- 定时器中断里的"1ms 到点了"标志 → 主循环做控制计算

### 🎤 30 秒口述版

> `volatile` 是告诉编译器：这个变量可能在你看不见的地方被改，每次用都必须真的去内存读，不许缓存到寄存器、不许优化掉。
>
> 环形缓冲区里 head 和 tail 恰恰是**被中断和主循环共享**的：中断里 rb_put 会改 head，
> 主循环却要靠读 head 来判断有没有新数据。如果 head 没加 volatile，
> 编译器会发现"这个循环体里没人改过 head"，就把它的值读到寄存器里一直用，
> 于是主循环永远看不到中断写进来的新数据——在调试版上正常、Release 版直接卡死的那种 bug。
>
> 不过 volatile 只解决"别乱优化"，不解决原子性和多核可见性。
> 好在环形缓冲区是单生产者单消费者：head 只有写者改、tail 只有读者改，
> 各自读对方的变量，只要保证读到的值是完整的一次访问，就不用加临界区。
> 如果同一侧有多个写者，那就要用关中断或者 C11 的 atomic 来保护了。

### 可能被追问

| 追问 | 怎么答 |
|---|---|
| `volatile` 能保证线程安全吗？ | 不能。它只阻止优化，不提供原子性和内存序。多线程/多核要靠锁或 `atomic` |
| 为什么只要给 head / tail 加，不用给 `buf[]` 也加？ | 数据本身是通过 head/tail 的先后关系来同步的：写者写完数据才更新 head，读者看到 head 变化就知道数据已经就位。索引是"同步点"，数据是"载荷" |
| 那会不会读到写了一半的数据？ | 在单写单读、且"先写数据后更新 head"的顺序下不会。这也是为什么要保证写数据的语句在更新 head 之前完成（必要时加编译屏障） |
| ISR 里调用 `rb_put` 要注意什么？ | 一是它必须足够快、不能阻塞；二是如果主循环也会写同一个索引，就要关中断保护 |

### 🧠 记忆钩子

> **`volatile` 治的是"编译器自作聪明"，不治"并发"。**

## 五、收工前回答 3：位操作宏少写一对括号会出什么事？

宏是**纯文本替换**，参数代进去之后才按运算符优先级解析。少一对括号，两种结局：编译报错，或者更糟——**静默算错**。

### 例子 1：`bit` 参数少了括号 → 静默算错

```c
#define SET_BIT(reg, bit)  ((reg) |= (1u << bit))   /* bit 这里没括号 */

SET_BIT(reg, flag ? 1 : 2);

/* 展开后是： ((reg) |= (1u << flag ? 1 : 2))
   因为 ?: 的优先级低于 <<，实际等价于：
              ((reg) |= ((1u << flag) ? 1 : 2))
   → flag 非 0 时去置 bit0，flag 为 0 时去置 bit1，
     和你想要的"置 bit1 或 bit2"完全不是一回事，而且编译器一声不吭 */
```

### 例子 2：`reg` 参数少了括号 → 直接编译报错

```c
#define SET_BIT(reg, bit)  (reg |= (1u << (bit)))   /* reg 这里没括号 */

uint32_t a = 1, b = 2;
SET_BIT(a + b, 3);

/* 展开后是： a + b |= (1u << 3)
   因为 + 的优先级高于 |=，实际等价于 (a + b) |= (1u << 3)
   → 报错：lvalue required as left operand of assignment
     （赋值号左边必须是"能被修改的左值"，而 a+b 是个表达式） */
```

### 例子 3：整个宏体没包一层括号 → 静默算错

```c
#define READ_BIT(reg, bit)  ((reg) >> (bit)) & 1u   /* 整体少了一层括号 */

int y = READ_BIT(x, 3) + 1;

/* 展开后是： (x >> 3) & 1u + 1
   因为 + 的优先级高于 &，实际等价于 (x >> 3) & (1u + 1)
                                          = (x >> 3) & 2
   → 拿到的是"第 4 位"，而你想要的是"第 3 位的值 + 1" */
```

### 正确写法（今天文件里用的）

```c
#define SET_BIT(reg, bit)    ((reg) |=  (1u << (bit)))
#define CLR_BIT(reg, bit)    ((reg) &= ~(1u << (bit)))
#define TOGGLE_BIT(reg, bit) ((reg) ^=  (1u << (bit)))
#define READ_BIT(reg, bit)   (((reg) >> (bit)) & 1u)
```

**两条规矩**：① 每个参数都用括号包起来；② 整个宏体再包一层括号。
另外用 `1u` 而不是 `1`，避免有符号类型左移 31 位时的未定义行为。

### 🎤 30 秒口述版

> 宏是纯文本替换，参数代进去之后才按优先级解析，所以少一对括号要么编译报错、要么更糟——静默算错。
>
> 比如 `SET_BIT(reg, bit)` 里如果 `bit` 没加括号，调用 `SET_BIT(reg, flag ? 1 : 2)` 会展开成
> `1u << flag ? 1 : 2`，因为 `?:` 优先级比 `<<` 低，实际变成 `(1u << flag) ? 1 : 2`，置的位完全不对。
> 再比如 `reg` 参数没加括号，`SET_BIT(a + b, 3)` 会展开成 `a + b |= 8`，
> 因为 `+` 优先级更高，等于 `(a+b) |= 8`，左边不是左值，直接报错。
> 还有一种隐蔽的：整个宏体没包括号，`READ_BIT(x,3) + 1` 会因为 `+` 比 `&` 优先级高而算错。
>
> 所以写这类宏的规矩是：**每个参数加括号，整体再加一层括号**；
> 另外用 `1u` 而不是 `1`，避免有符号左移 31 位的坑。

### 🧠 记忆钩子

> **宏没有"函数调用"的保护壳，所以括号要自己穿两层。**
